## Controls (valid worlds)

- misbound store + operators: E2 0.09, E5 FR 0.34
- restart (store file of full+ops): same answers 30/30, accuracy after restart 1.000, empty store on positive items 0.000, truncated refused 30/30, changed refused 30/30

My reading (exploratory): (i) the memory mechanism works: certified selection + operators answer every item, reject every lure, survive the restart; (ii) the 0.5B reader is the bottleneck: with exactly the same certified notes it reaches about half the accuracy and invents an answer to almost every lure (false recall 0.95), so the reasoning should stay in the operators; (iii) selection matters too (lex3 vs struct3 with operators 0.69 vs 1.00); (iv) the LM slot encoder fails clearly (all slots 0.22). A post-hoc look at the raw replies (after the run) shows mostly format errors: objects without their adjective ("umbrella" for "tiny umbrella"), capitalised or base-form verbs ("Painted", "measure"), days answered as weekdays ("Wednesday"); the partner normalisation was applied in 837/1,200 records (the model mostly repeats the first person when there is no second one).

C. MY PROPOSAL FOR THE NEXT STEP (please give your own recommendation first)

Goal: the language interface, with the reasoning kept in the operators. Round 3.4 step 2 = LM as the interface only:
1. Encoder by constrained choice instead of free generation: for each slot the LM scores candidate spans taken generically from the note itself (all 1-2-word spans, plus numbers, plus "none" for the partner), with the log-likelihood scoring that worked for single details in S1 (score_candidates exists). No template knowledge in the candidate generator.
2. Goal/question parsing the same way: the LM picks the query type from a fixed list and the cue values from spans of the question; the operators answer.
3. History operators with unknown fields first (your backlog item), so the LM's uncertain slots stay uncertainty.
4. Qualification on HELD-OUT data: new world series and the free wordings of the 3.2 templates not used for development; the same qualification rule as 3.2 (all slots >= 0.95, positives within 0.02 of the template encoder, lure false recall <= 0.05), fixed before the run; then the 3.3/3.4 environment with the qualified encoder.
5. Model: qwen2.5-0.5b and qwen3-0.6b both scored (cheap with candidate scoring); a larger model only if both fail, as a separate measured decision.
Open questions to you: is span scoring a fair test of "the LM writes the memory" or too much help? What would you change in the qualification? Should the cache baseline and context-dependent historical queries come before the language interface?
